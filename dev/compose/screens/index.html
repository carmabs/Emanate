    Compose screens¶

    An Emanate screen splits the work between three pieces, so that each one has a single job:

    Piece Job Example
    The ViewModel Holds the state and decides what happens when the user does something. It knows nothing about Compose. HomeViewModel
    The screen content (EmaScreenContent) Draws the state with Compose and reports what the user does. It keeps no data of its own. HomeScreenContent
    The registration (emaScreen) The glue. It creates the ViewModel, connects it to the content and to the lifecycle, puts the screen in your navigation graph and receives its events. The NavHost block

    The information always travels the same way. In the home screen of the sample, the admin taps the button to create a user:

    1. The user taps Create, and the screen content sends the action CreateClicked.
    2. The ViewModel decides what that means. Whenever its state changes, the screen content draws it again.
    3. Here the answer is a one-off: the ViewModel publishes the event CreateClicked, and the onEvent of emaScreen opens the next screen.

    The screen never changes the state itself: it only sends actions and draws whatever state the ViewModel gives it. Because of that, the same content can be shown in a preview, in a test or in a real app without changes.

    This page follows the life of a screen, from writing it to using it. You need the emanate-android and emanate-compose-android artifacts. To register the screens in a Navigation Compose graph, as in the examples, you also need emanate-compose-android-nav2: the other artifacts don't depend on any navigation library.

    Screen content¶

    This is the part you will write most often: the Compose code of the screen. You create one class that implements EmaScreenContent and fill in onState, which receives the current state and draws it. When the user presses a button, you do not change anything: you send an action with actions.dispatch(...), and the ViewModel answers with a new state that makes onState run again.

    class HomeScreenContent : EmaScreenContent<HomeState, HomeAction> {

    @Composable
    override fun onState(
        state: HomeState,
        actions: EmaActionDispatcher<HomeAction>
    ) {
        // Draw the state. Send user input with actions.dispatch(...)
    }
}

    EmaScreenContent<S, A> takes the type of the state and the type of the actions, and has two members:

    Member Purpose
    onState(state, actions) Required. Draws the state. It is a @Composable.
    onBack(state): A? The action to send when back is pressed, or null. See Back handling. Optional.

    The screen content doesn't receive the events: they are handled where the screen is registered, as explained in Handling the events.

    Keep the screen content free of state: it is a stateless description, created once per screen. Anything that must survive belongs in the state of the ViewModel.

    Registering the screen¶

    A screen content on its own is just a description: nothing shows it yet. Registering it means adding it as a destination of your NavHost, as you would with Compose Navigation's composable(...), but with emaScreen, which also creates the ViewModel and wires everything together. This is also where you decide what happens when the ViewModel sends an event, such as navigating to another screen. emaScreen is in the emanate-compose-android-nav2 artifact. If you use another navigation, place the screen with EmaScreen, which is in emanate-compose-android.

    NavHost(
    navController = navController,
    startDestination = HomeScreenContent::class.routeId
) {
    emaScreen(
        screenContent = HomeScreenContent(),
        viewModel = { createHomeViewModel() },
        onEvent = { navigator.handleHome(it) }
    )
}

    Provide the ViewModels with an injector

    createHomeViewModel() stands for whatever creates the ViewModel in your project. It is a good idea to use a dependency injector like Koin for it: the ViewModel and its use cases are declared once, in a module, and the screen only asks for the type. Declare the ViewModels with factory, so each screen gets its own:

    // The module of the injector
val uiModule = module {
    factoryOf(::HomeViewModel)
    factory { HomeState.DEFAULT }
}

// The screen only asks for its ViewModel
emaScreen(
    screenContent = HomeScreenContent(),
    viewModel = { get<HomeViewModel>() },
    onEvent = { navigator.handleHome(it) }
)

    See Dependency injection.

    Parameter Purpose
    screenContent The screen content.
    viewModel A lambda that creates the ViewModel. It is called once, when the screen is opened, and receives the EmaStateStore of the screen for a backup. See Dependency injection.
    onEvent Receives every event of the screen. See Handling the events.
    routeId The route. By default ScreenContent::class.routeId, which is unique per class.
    initializerSupport How to read the initializer from the route. See Navigation.
    transitionAnimation EmaAnimTransition(enterTransition, exitTransition, popEnterTransition, popExitTransition). The pop transitions default to the enter and exit ones.

    The parameters you will use most are the first three. The rest have a default value, so add them only when you need them. For example, a screen that enters sliding from the right:

    emaScreen(
    screenContent = ProfileCreationScreenContent(),
    viewModel = { createProfileCreationViewModel() },
    transitionAnimation = EmaAnimTransition(
        enterTransition = { slideInHorizontally { width -> width } },
        exitTransition = { slideOutHorizontally { width -> width } }
    ),
    onEvent = { navigator.handleProfileCreation(it) }
)

    Showing a screen as a dialog¶

    Some screens are shown over the previous one, in a dialog, instead of replacing it. Register them with emaDialog instead of emaScreen. Everything else is the same: the screen content, the ViewModel, the events and the initializer of the route. Only the transitions change, as a dialog has none, for dialogProperties, the DialogProperties of Compose:

    emaDialog(
    screenContent = FilterScreenContent(),
    viewModel = { createFilterViewModel() },
    dialogProperties = DialogProperties(usePlatformDefaultWidth = false),
    onEvent = { navigator.handleFilter(it) }
)

    You open it like any other screen, with navController.navigate(FilterScreenContent::class.routeId).

    This is a destination of the graph that looks like a dialog. For a small dialog inside a screen, like a confirmation, use the state instead: see Dialogs.

    Handling the events¶

    An event is something that must happen once, like showing a toast or opening another screen, as opposed to the state, which is always there. Every event of the screen arrives at one place: the onEvent lambda of emaScreen. After it returns, the event is consumed and it will not arrive again.

    onEvent is written in the graph, inside your activity or composable, so everything an event may need is at hand: the NavController or the navigator to navigate, and the Context to show a toast or open another app.

    val context = LocalContext.current

NavHost(navController, startDestination = ProfileCreationScreenContent::class.routeId) {
    emaScreen(
        screenContent = ProfileCreationScreenContent(),
        viewModel = { createProfileCreationViewModel() },
        onEvent = { event ->
            when (event) {
                ProfileCreationEvent.DialogConfirmationAccepted -> navController.navigateBack()
                is ProfileCreationEvent.ProfileSaved ->
                    Toast.makeText(context, "Profile saved", Toast.LENGTH_SHORT).show()
            }
        }
    )
}

    As every event arrives at the same when, the compiler warns you when a new event is not handled. When the when grows, move it to a function of your navigator, as the sample does with navigator.handleHome(it).

    onEvent must return quickly: the next events wait for it. Navigating or showing a toast is immediate. For something that takes time, like a snackbar, launch it in a coroutine scope of yours:

    val scope = rememberCoroutineScope()
val snackbarHostState = remember { SnackbarHostState.DEFAULT }

NavHost(navController, startDestination = ProfileCreationScreenContent::class.routeId) {
    emaScreen(
        screenContent = ProfileCreationScreenContent(),
        viewModel = { createProfileCreationViewModel() },
        onEvent = { event ->
            when (event) {
                is ProfileCreationEvent.ProfileSaved -> scope.launch { snackbarHostState.showSnackbar("Saved") }
                ProfileCreationEvent.DialogConfirmationAccepted -> navController.navigateBack()
            }
        }
    )
}

    Lifecycle¶

    A screen goes through moments: it is created, it appears, the user leaves to another app, it comes back, it is destroyed. The ViewModel often needs to know, for example to load data when the screen appears or to stop listening to something when it is paused. You do not have to observe the lifecycle yourself: the screen does it and passes each moment on to the ViewModel.

    The screen connects the ViewModel to the lifecycle of its destination:

    Lifecycle event The ViewModel receives
    ON_CREATE, the first time The EmaInitializer of the screen
    ON_START EmaLifecycle.Started
    ON_RESUME EmaLifecycle.Resumed
    ON_PAUSE EmaLifecycle.Paused
    ON_STOP EmaLifecycle.Stopped
    The screen leaves the composition EmaLifecycle.Paused and EmaLifecycle.Stopped
    The destination is removed EmaLifecycle.Destroyed, and it is closed

    The state is collected with collectAsStateWithLifecycle and the events while the lifecycle is STARTED.

    Previews¶

    Every screen content has its preview, annotated with @PreviewLightDark to see it in light and dark mode, inside the theme of the app.

    The @PreviewLightDark of Android Studio draws a composable without running the app, which makes designing the UI much faster. But a preview cannot create a real ViewModel, so you give it a state by hand and see how the screen looks with it. Writing one preview per interesting state (empty, loading, error...) is a cheap way to check them all.

    Inside the IDE preview there is no ViewModel, so call onState directly with a state and an empty dispatcher:

    @PreviewLightDark
@Composable
private fun PreviewNormal() {
    EmaSampleTheme {
        ProfileCreationScreenContent().onState(
            state = ProfileCreationState.DEFAULT.copy(name = "Carlos", surname = "Mateo"),
            actions = EmaActionDispatcher.EMPTY
        )
    }
}

    Using a screen without a navigation graph¶

    emaScreen needs a NavHost. But not every app uses Navigation Compose: an activity may show a single screen, or you may want an Emanate screen as just a part of a bigger layout, like a counter inside a page. For those cases there is EmaScreen, a composable that you place wherever you want, like a Text or a Column.

    EmaScreen is in fact what emaScreen draws inside each destination, so it does the same work: it creates the ViewModel, connects it to the lifecycle, draws the state with the screen content, sends the back button actions and passes every event to onEvent. The only thing missing is the graph.

    A screen in an activity¶

    The most common case: an activity that shows one Emanate screen and nothing else. Imagine a counter with a + button that warns the user when it reaches 10.

    class CounterActivity : ComponentActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            EmaSampleTheme {
                EmaScreen(
                    vm = { CounterViewModel() },
                    screenContent = CounterScreenContent(),
                    onEvent = { event ->
                        when (event) {
                            CounterEvent.LimitReached ->
                                Toast.makeText(this, "You reached 10", Toast.LENGTH_SHORT).show()
                        }
                    }
                )
            }
        }
    }
}

    The parameters are the ones of emaScreen, with shorter names:

    Parameter Purpose
    vm A lambda that creates the ViewModel. It is called only the first time, as in emaScreen.
    screenContent The screen content.
    onEvent Receives every event of the screen, as in Handling the events.
    initializer The initializer of the screen. Here there is no route to read it from, so you pass it directly. Optional.
    previewRenderState The state to draw in a preview. See Previews of a bigger layout. Optional.

    For example, to open the counter starting at 5, pass the initializer yourself:

    EmaScreen(
    initializer = CounterInitializer(start = 5),
    vm = { CounterViewModel() },
    screenContent = CounterScreenContent(),
    onEvent = { /* ... */ }
)

    A screen inside a bigger layout¶

    As EmaScreen is a composable, it can be one piece of a page. Here the counter sits under a title and over a button that is not part of it:

    @Composable
fun DashboardPage(onSettingsClicked: () -> Unit) {
    Column {
        Text("Dashboard", style = MaterialTheme.typography.headlineMedium)

        EmaScreen(
            vm = { CounterViewModel() },
            screenContent = CounterScreenContent(),
            onEvent = { /* ... */ }
        )

        Button(onClick = onSettingsClicked) { Text("Settings") }
    }
}

    The ViewModel lives as long as the activity (or the destination of the graph) that contains the page, not as long as the composable. If the counter is inside an if and disappears, its ViewModel receives Paused and Stopped, and keeps its state: when the counter appears again, it shows the same number.

    Previews of a bigger layout¶

    previewRenderState is the state that the screen shows instead of the real one when it is drawn in the preview of Android Studio:

    Where the screen is drawn What it shows
    In the app, on a device The real state, the one of the ViewModel. previewRenderState is ignored.
    In the preview of Android Studio previewRenderState. The ViewModel is not even created.

    You need it because a preview cannot create the ViewModel, so without previewRenderState the screen has no state to draw and its space stays empty. With it, you see the whole page as it will look:

    @Composable
fun DashboardPage() {
    Column {
        Text("Dashboard")
        EmaScreen(
            vm = { CounterViewModel() },
            screenContent = CounterScreenContent(),
            onEvent = { /* ... */ },
            // Only for the preview: the app shows the real count of the ViewModel
            previewRenderState = CounterState.DEFAULT.copy(count = 3)
        )
    }
}

@PreviewLightDark
@Composable
private fun PreviewDashboard() {
    // The title and a counter with the number 3
    DashboardPage()
}
